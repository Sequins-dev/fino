# The TypeScript coordination layer

<Rule />

<Lead>A runtime boundary designed to make native crossings rare, coarse, and boring.</Lead>

<Footer>Coordinate in TypeScript · compute at the edge</Footer>

<Notes>This talk is about where a runtime should draw its language boundary. Fino does not try to replace kernels, cryptography, databases, or mature protocol engines with TypeScript. It keeps the coordination around those primitives in TypeScript, then crosses into native code only at the point where native work is unavoidable.</Notes>

---

<Eyebrow>01 · Start with the work</Eyebrow>

## Most runtime work is not a kernel

<Grid columns={3}>
  <Panel title="Compute"><div>Compress a block.</div><div>Encrypt a record.</div><div>Parse a packet number.</div></Panel>
  <Panel title="Coordinate" tone="amber"><div>Schedule a timer.</div><div>Move bytes between queues.</div><div>Apply cancellation and backpressure.</div></Panel>
  <Panel title="Expose" tone="coral"><div>Create the `Request`.</div><div>Route it through middleware.</div><div>Return application values.</div></Panel>
</Grid>

<Callout label="Context">Native code excels at dense primitives. A runtime spends much of its time arranging when those primitives run and what happens around them.</Callout>

<Notes>The architectural mistake is to classify an entire subsystem as native because one part contains a hard algorithm. HTTP/3 contains cryptography and congestion control, but the runtime also coordinates sockets, timers, streams, requests, handlers, and cancellation. Those are different kinds of work with different ideal ownership.</Notes>

<Eyebrow>02 · The boundary rule</Eyebrow>

## Put each kind of work where it belongs

<div style={{ display: 'grid', gap: '.65em', width: '100%' }}>
  <Layer label="Application" detail="Handlers, middleware, schemas, observability, workflows" tone="coral">TypeScript objects remain TypeScript objects</Layer>
  <Layer label="Coordination" detail="State machines, queues, timers, cancellation, routing, policy" tone="cyan">TypeScript owns the moving system</Layer>
  <Layer label="Primitive" detail="syscalls, crypto, compression, protocol kernels, SQLite" tone="ink">Native code performs irreducible native work</Layer>
</div>

<Callout label="Rule">Cross once for a primitive. Continue coordinating where the state and application objects already live.</Callout>

<Notes>This is the inversion at the center of Fino. Native code is not the architecture with a JavaScript façade. TypeScript is the architecture, and native code is a set of carefully chosen edges. That keeps the application-facing model and the coordination model in one place.</Notes>

---

<Eyebrow>03 · What coordination means</Eyebrow>

## TypeScript owns the moving parts

<Grid columns={2}>
  <Panel title="State"><div>Connections, streams, requests, transactions, and protocol phases share one object model.</div></Panel>
  <Panel title="Time" tone="amber"><div>Timers, readiness, retries, cancellation, and backpressure are decided beside that state.</div></Panel>
  <Panel title="Policy" tone="coral"><div>Routing, limits, caching, batching, security rules, and error mapping remain programmable.</div></Panel>
  <Panel title="Application"><div>Values move into handlers without being reconstructed from a native mirror.</div></Panel>
</Grid>

<Notes>Coordination is branchy, stateful, and closely tied to application-visible objects. Moving it into native code creates a second object graph and a second lifecycle model. Keeping it in TypeScript lets the same references flow from protocol state to middleware to user code.</Notes>

<Eyebrow>04 · Native has two jobs</Eyebrow>

## Go native for necessity, not prestige

<Grid columns={2}>
  <Panel title="Direct system access" tone="coral"><div>Socket and file syscalls</div><div>readiness and platform handles</div><div>memory and pointer operations</div></Panel>
  <Panel title="Existing complex engines" tone="amber"><div>TLS, crypto, and compression</div><div>ngtcp2, nghttp2, and nghttp3</div><div>SQLite and other mature libraries</div></Panel>
</Grid>

<Callout label="Selection test">If the operating system or a mature native library already owns the hard part, call it. Otherwise, keep the behavior with the TypeScript system that consumes it.</Callout>

<Notes>These are pragmatic edges. Reimplementing SQLite, TLS, or the kernel in TypeScript would be wasteful and risky. But wrapping those libraries in a large native coordination layer would also be wasteful. Fino uses the existing engine and keeps the surrounding decisions in TypeScript.</Notes>

<Eyebrow>05 · The ideal crossing</Eyebrow>

## Make the boundary boring

<Flow>
  <FlowNode number="TS" title="Choose storage" detail="Allocate or reuse the buffer where coordination already happens." />
  <Arrow />
  <FlowNode number="FFI" title="Pass facts" detail="Pointer, length, offsets, flags, and small scalar handles." tone="coral" />
  <Arrow />
  <FlowNode number="NATIVE" title="Do one primitive" detail="Read or write caller-owned memory, or invoke the existing engine." tone="amber" />
  <Arrow />
  <FlowNode number="TS" title="Keep moving" detail="Use the same bytes and objects for the next decision." />
</Flow>

<Callout label="Interface shape">Buffers and scalars go in. A status, length, or stable handle comes back.</Callout>

<Notes>The most important FFI optimization is not a faster call instruction. It is an interface that carries almost nothing. The TypeScript side already owns typed-array storage. Native code receives a pointer and length, operates on that memory, and returns only enough information for TypeScript to continue.</Notes>

<Eyebrow>06 · The result</Eyebrow>

## Marshalling is nearly gone

<Grid columns={2}>
  <Panel title="A chatty boundary" tone="coral"><div>Convert a JS object graph.</div><div>Build native structs.</div><div>Run the primitive.</div><div>Rebuild JS result objects.</div></Panel>
  <Panel title="The Fino boundary"><div>Keep application state in TypeScript.</div><div>Share existing byte storage.</div><div>Pass pointer + length.</div><div>Return into the same state.</div></Panel>
</Grid>

<Callout label="What disappeared">No mirrored `Request`. No native `Headers` wrapper. No serialized protocol state. No field-by-field result reconstruction.</Callout>

<Notes>There is still unavoidable call overhead and scalar decoding, so “zero marshalling” is not a claim that a crossing costs zero cycles. It means the architectural marshalling layer is absent: Fino does not translate its application object graph into a native twin and back. Large payloads stay in shared buffers, while small results return as scalars or handles.</Notes>

<Eyebrow>07 · One heap</Eyebrow>

## The coordination layer can see the whole decision

<Grid columns={2}>
  <Panel title="Skip"><div>If state proves a timer, query, or conversion is unchanged, TypeScript can avoid the native call entirely.</div></Panel>
  <Panel title="Batch" tone="amber"><div>Queues and policy can combine many small operations into one coarse syscall or library call.</div></Panel>
  <Panel title="Reuse" tone="coral"><div>Buffers, views, and application objects retain identity instead of being rebuilt at every layer.</div></Panel>
  <Panel title="Optimize"><div>V8 sees stable shapes, branches, and call sites across protocol and application code.</div></Panel>
</Grid>

<Notes>This is where TypeScript can produce an end-to-end performance advantage. The win is not that V8 executes a cryptographic round faster than optimized C. The win is that the coordination layer can decide not to call, batch calls, reuse storage, and pass existing objects directly to their consumers.</Notes>

<Eyebrow>08 · Why fewer crossings win</Eyebrow>

## The fastest boundary is the one you do not need

<Flow>
  <FlowNode number="01" title="No mirror" detail="One state model instead of synchronized JS and native copies." />
  <Arrow />
  <FlowNode number="02" title="No handoff" detail="Direct references replace generic events and wrapper queues." tone="coral" />
  <Arrow />
  <FlowNode number="03" title="No copy" detail="Typed-array views keep bytes in their original storage." tone="amber" />
  <Arrow />
  <FlowNode number="04" title="No call" detail="Local state suppresses redundant native queries." />
</Flow>

<Callout label="Performance model">Optimize total work across the boundary—not the isolated speed of the native loop.</Callout>

<Notes>A microbenchmark can prove that a native loop is faster and still recommend the slower architecture. The system pays for conversion, ownership, callbacks, wrappers, and result construction around that loop. Fino profiles the entire path and treats avoided work as the highest-value optimization.</Notes>

<Eyebrow>09 · What profiling taught us</Eyebrow>

## The measured wins all removed coordination work

<div style={{ display: 'grid', gap: '.65em', width: '100%' }}>
  <Evidence value="+11.4%" title="Pass the existing stream reference directly" before="event object + duplicate queue" after="one internal handoff" tone="coral" />
  <Evidence value="+8.3%" title="Keep a common URL path in TypeScript" before="generic work on every request" after="skip work the local state rules out" />
  <Evidence value="+4.8%" title="Reuse boundary scratch storage" before="allocate around each callback" after="overwrite one retained buffer" tone="amber" />
</div>

<Notes>These examples are deliberately grouped by lesson rather than subsystem. The largest measured improvement removed an unnecessary event abstraction between TypeScript components. Another added a common-case URL path entirely in TypeScript. Another reused storage at a native callback boundary. None required moving the coordination layer into native code.</Notes>

<Eyebrow>10 · The pattern repeats</Eyebrow>

## Different subsystems, the same split

<Grid columns={3}>
  <Panel title="Networking"><div>Native owns sockets, crypto, and codec kernels. TypeScript owns connections, streams, timers, requests, and routing.</div></Panel>
  <Panel title="Databases" tone="amber"><div>SQLite owns planning and execution. TypeScript owns statements, values, migrations, errors, and programmable I/O policy.</div></Panel>
  <Panel title="Data formats" tone="coral"><div>Native compression may transform blocks. TypeScript metadata and typed-array views keep uncompressed data zero-copy.</div></Panel>
</Grid>

<Callout label="Consistency">The coordination layer stays uniform even when the primitive underneath changes completely.</Callout>

<Notes>This boundary scales across the runtime. The native implementation can be a syscall, a C library, or no native code at all. The TypeScript side keeps the same responsibilities: ownership of application-visible state, scheduling, policy, and composition.</Notes>

<Eyebrow>11 · Boundary smell</Eyebrow>

## A chatty FFI usually means the cut is wrong

<Grid columns={2}>
  <Panel title="Warning signs" tone="coral"><div>Field-by-field getters</div><div>mirrored object graphs</div><div>callbacks for every state change</div><div>native wrappers returned to application code</div></Panel>
  <Panel title="Better shapes"><div>one operation over a buffer</div><div>one batch over many entries</div><div>one stable opaque handle</div><div>one small scalar result</div></Panel>
</Grid>

<Callout label="Diagnostic">If the binding needs an object mapper, move the boundary closer to the primitive.</Callout>

<Notes>Chatty bindings turn inexpensive local decisions into repeated cross-language operations. They also spread ownership rules across two heaps. The repair is usually not to optimize every getter; it is to lift coordination back into TypeScript and expose a coarser native primitive.</Notes>

<Eyebrow>12 · Decision rule</Eyebrow>

## Choose the side that minimizes total work

<div style={{ width: '100%' }}>
  <Decision when="A syscall or mature engine owns the primitive" choose="native edge" reason="Use the implementation that already has the required system access or complexity." tone="coral" />
  <Decision when="State and policy determine what happens next" choose="TypeScript" reason="Keep the decision beside the objects, queues, timers, and consumers it coordinates." />
  <Decision when="The boundary would be called repeatedly" choose="batch or move it" reason="Prefer one coarse operation over many individually fast crossings." tone="amber" />
  <Decision when="Data can remain in existing storage" choose="pointer + view" reason="Share bytes; return a length, status, offset, or stable handle." />
</div>

<Notes>The decision is made per operation, not per subsystem. A TypeScript network stack can call a native packet engine. A TypeScript database API can call SQLite. The right cut is the one that minimizes total conversion, synchronization, copying, and ownership work.</Notes>

<Eyebrow>Conclusion</Eyebrow>

# Keep native at the edges

<Rule />

<Lead>Let TypeScript coordinate the system. Let native code touch the kernel, run the mature engine, or operate directly on shared bytes—then get out of the way.</Lead>

<Footer>Fewer crossings · no mirrored state · almost no marshalling</Footer>

<Notes>The result is not merely a smaller native core. It is a runtime with fewer handoffs, fewer copies, fewer wrapper objects, and more opportunities to skip work entirely. The boundary becomes infrastructure, while the runtime behavior remains visible and optimizable in TypeScript.</Notes>
