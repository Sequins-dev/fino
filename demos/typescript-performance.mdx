# The TypeScript coordination layer

<Rule />

<Lead>A runtime architecture built by pushing native code to the edges—and keeping the decisions in TypeScript.</Lead>

<Footer>Coordinate in TypeScript · compute at the edge</Footer>

<Notes>This is a story about architectural boundaries, not a contest between languages. Fino uses native code aggressively where native work is irreducible. The performance result comes from being equally aggressive about keeping policy, ownership, and coordination on one side of that boundary.</Notes>

---

## The question is not which language is faster

<Grid columns={3}>
  <Panel title="Local speed"><div>How fast does one loop execute?</div></Panel>
  <Panel title="Boundary cost" tone="amber"><div>What must be copied, converted, pinned, synchronized, or reconstructed?</div></Panel>

<Callout label="Measure the system">A faster primitive can still produce a slower path when the architecture surrounds it with handoffs.</Callout>

<Notes>Language comparisons usually isolate the compute loop. Runtime architecture cannot. It must account for preparing the call, transferring ownership, synchronizing state, returning the result, and making the next decision. The useful comparison is total work from intent to outcome.</Notes>

<Eyebrow>Chapter I · Policy and state</Eyebrow>

# Coordination is the runtime

<Rule />

<Lead>The runtime is not just the primitive. It is everything that decides when, whether, and how that primitive should run.</Lead>

<Footer>Chapter I · Keep the next decision with its facts</Footer>

<Notes>This chapter establishes why coordination is first-class performance work. It is branchy, stateful, and application-facing. Treating it as a thin wrapper around native code puts the majority of runtime behavior on the wrong side of the boundary.</Notes>

---

<Eyebrow>I · What coordination contains</Eyebrow>

## Coordination is where the runtime decides

<Grid columns={2}>
  <Panel title="State"><div>Which operations exist?</div><div>Which objects and buffers do they own?</div></Panel>
  <Panel title="Time" tone="amber"><div>What is ready now?</div><div>What should wait, retry, or expire?</div></Panel>
  <Panel title="Policy" tone="coral"><div>What is allowed, cached, batched, routed, or rejected?</div></Panel>
  <Panel title="Composition"><div>Which middleware, consumer, or continuation receives the result?</div></Panel>
</Grid>

<Notes>These are not peripheral concerns. They determine whether the primitive runs at all, how much work it receives, and what happens afterward. The coordination layer owns the control plane of the runtime.</Notes>

---

<Eyebrow>I · Shape of the work</Eyebrow>

## Coordination is a graph, not a kernel

<Grid columns={3}>
  <Panel title="Branchy"><div>Common cases, exceptional cases, policy gates, and cancellation.</div></Panel>
  <Panel title="Stateful" tone="amber"><div>Decisions depend on objects that persist across many operations.</div></Panel>
  <Panel title="Connected" tone="coral"><div>One event can affect queues, timers, consumers, and future work.</div></Panel>
</Grid>

<Callout label="Different optimization">Dense loops reward instruction-level speed. Coordination rewards locality of information and the ability to remove work.</Callout>

<Notes>Native code is excellent at tight, predictable loops. Coordination has the opposite shape. It is a changing graph of state and policy. Its performance depends less on one branch executing quickly and more on avoiding duplicated state, redundant calls, and unnecessary handoffs.</Notes>

<Callout label="Synchronization tax">Every mirrored fact needs a rule for creation, mutation, invalidation, error, and destruction.</Callout>

<Notes>The problem is not only copying data. It is maintaining two authoritative representations of one operation. Each field requires synchronization rules, each lifetime requires coordination, and every failure path must keep both sides consistent.</Notes>

<Eyebrow>Chapter II · Ownership and lifetime</Eyebrow>

# Reuse is an architectural decision

<Rule />

<Lead>Arenas and pools are not just allocation tricks. They make ownership, lifetime, and admission visible to the coordination layer.</Lead>

<Footer>Chapter II · Allocate by lifetime, not by operation</Footer>

<Notes>This chapter moves from control flow to memory. The same architectural principle applies: reuse works best where lifetimes are understood. TypeScript can own storage and pooling policy while native code operates directly on the selected bytes.</Notes>

---

<Eyebrow>II · Allocation pressure</Eyebrow>

## Allocation is coordination in disguise

<Grid columns={3}>
  <Panel title="Choose"><div>How much storage is needed?</div></Panel>
  <Panel title="Own" tone="amber"><div>Which operation may retain it, and for how long?</div></Panel>
  <Panel title="Release" tone="coral"><div>When is reuse safe, and what invalidates old views?</div></Panel>
</Grid>

<Callout label="The real cost">Allocation policy is lifetime policy. Moving it away from coordination hides the information needed to reuse safely.</Callout>

<Notes>An allocator can make obtaining bytes cheap, but the runtime still needs to know when those bytes are safe to reuse. That is a coordination question. The best memory strategy aligns storage lifetime with an operation the TypeScript layer already understands.</Notes>

---

<Eyebrow>II · Arena pattern</Eyebrow>

## An arena makes lifetime explicit

<Flow>
  <FlowNode number="01" title="Reserve once" detail="Create one backing buffer for a known lifetime." />
  <Arrow />
  <FlowNode number="02" title="Slice views" detail="Advance a cursor and return typed-array views." tone="coral" />
  <Arrow />
  <FlowNode number="03" title="Consume" detail="Use every view before the epoch ends." tone="amber" />
  <Arrow />
  <FlowNode number="04" title="Reset" detail="Move one cursor back to zero." />
</Flow>

<Callout label="Simple contract">The arena owns storage. Callers borrow views. Reset ends the borrowing epoch.</Callout>

<Notes>Fino's arena is a bump allocator implemented directly in TypeScript over one ArrayBuffer. Allocation creates a view at the current cursor. Reset is O(1). If capacity is exceeded, the operation safely falls back to standalone storage rather than turning optimization into a failure mode.</Notes>

---

<Eyebrow>II · Borrow, do not transfer</Eyebrow>

## Views are cheaper than ownership transfers

<Grid columns={2}>
  <Panel title="Transfer ownership" tone="coral"><div>Allocate another buffer.</div><div>copy or detach bytes</div><div>coordinate release</div></Panel>
  <Panel title="Borrow a view"><div>Keep one backing store.</div><div>carry offset + length</div><div>reuse when the epoch ends</div></Panel>
</Grid>

<Callout label="Typed arrays">A view can describe exactly the bytes a primitive needs without creating a second owner.</Callout>

<Notes>Typed-array views are an architectural tool. They let TypeScript describe a region of existing storage precisely. The FFI can honor the view's byte offset and length, so native code receives the correct region without requiring a copied, zero-offset buffer.</Notes>

---

<Eyebrow>II · Bulk lifetime</Eyebrow>

## Reset the epoch, not every object

<Grid columns={3}>
  <Metric value="1" label="backing buffer" note="reserved for the lifetime" />
  <Metric value="N" label="cheap views" note="cursor increments, not backing stores" tone="coral" />
  <Metric value="O(1)" label="bulk reset" note="one lifetime transition" tone="amber" />
</Grid>

<Notes>The arena replaces many independent allocation and release decisions with one epoch. That does not mean every view is free, but it removes repeated backing-store allocation and makes release a single explicit event.</Notes>

---

<Eyebrow>II · Pooling</Eyebrow>

## Pools turn creation into admission control

<Grid columns={2}>
  <Panel title="Without a pool" tone="coral"><div>Create on demand.</div><div>pay setup repeatedly</div><div>discover overload late</div></Panel>
  <Panel title="With a pool"><div>Retain warm capacity.</div><div>dispatch by availability</div><div>bound waiting explicitly</div></Panel>
</Grid>

<Callout label="Coordination again">The performance feature is not merely reuse. It is making capacity, queueing, timeout, and shutdown policy explicit.</Callout>

<Notes>Pooling amortizes expensive creation, but its deeper value is controlled coordination. The pool knows its width, pending work, queue bounds, timeouts, and failure behavior. Those policies remain in TypeScript where they can compose with application intent.</Notes>

---

<Eyebrow>II · Safe reuse</Eyebrow>

## Reuse must be bounded

<div style={{ width: '100%' }}>
  <Decision when="Capacity is available" choose="reuse" reason="Take the warm object or the next arena region." />
  <Decision when="The arena is full" choose="fall back" reason="Allocate safely; optimization must not become a failure mode." tone="amber" />
  <Decision when="The queue is full" choose="apply policy" reason="Reject, wait, shed, or backpressure deliberately." tone="coral" />

<Notes>Unbounded pooling turns performance optimization into memory retention. Unsafe arena reuse turns speed into aliasing bugs. The coordination layer has enough context to bound both: capacity, epoch, queue depth, deadlines, and failure policy.</Notes>

---

<Eyebrow>II · Chapter principle</Eyebrow>

## Reuse where the lifecycle is already known

<Grid columns={3}>
  <Panel title="Arena"><div>Many temporary byte regions share one short lifetime.</div></Panel>
  <Panel title="Pool" tone="amber"><div>Expensive resources survive across bounded units of work.</div></Panel>
  <Panel title="Direct view" tone="coral"><div>Existing storage already has the right owner and lifetime.</div></Panel>
</Grid>

<Callout label="Chapter II">Reuse follows ownership. Coordination knows ownership. Keep reuse policy with coordination.</Callout>

<Notes>Arenas, pools, and direct typed-array views are three versions of the same idea: shape allocation around a lifetime the runtime already understands. This reduces churn without moving ownership into native code.</Notes>

<Eyebrow>Chapter III · The native edge</Eyebrow>

# Make the boundary boring

<Rule />

<Lead>The best FFI carries only enough information for native code to perform one primitive over storage TypeScript already owns.</Lead>

<Footer>Chapter III · Buffers, pointers, scalars, handles</Footer>

<Notes>This chapter defines the desired native interface. The goal is not a rich cross-language object model. It is a deliberately impoverished boundary made of buffers, offsets, lengths, scalars, and stable opaque handles.</Notes>

---

<Eyebrow>III · Interface shape</Eyebrow>

## Carry facts, not objects

<Grid columns={2}>
  <Panel title="Facts cross"><div>pointer + length</div><div>offsets and flags</div><div>small scalar values</div><div>stable opaque handles</div></Panel>
  <Panel title="Objects stay" tone="coral"><div>requests and responses</div><div>queues and streams</div><div>policy and errors</div><div>application identity</div></Panel>
</Grid>

<Callout label="Boundary goal">Describe the primitive completely without exporting the runtime's object graph.</Callout>

<Notes>A native function should not need to understand the application's Request, stream, queue, or policy object. It needs the facts required to perform its operation. This prevents the FFI from becoming a second runtime model.</Notes>

<Eyebrow>III · Pointer discipline</Eyebrow>

## Pointers are coordinates, not ownership

<Grid columns={3}>
  <Panel title="Pointer"><div>Where the region begins.</div></Panel>
  <Panel title="Length" tone="amber"><div>How much memory is valid.</div></Panel>
  <Panel title="Lifetime" tone="coral"><div>How long the caller guarantees it remains usable.</div></Panel>
</Grid>

<Callout label="Narrow contract">Native may operate on the region. TypeScript retains the object, backing store, and lifecycle.</Callout>

<Notes>The pointer should not imply that native code owns a new object graph. It is a coordinate into caller-owned memory for the duration of one operation. Keeping that distinction sharp makes the FFI safer and cheaper.</Notes>

---

<Eyebrow>III · Crossing frequency</Eyebrow>

## Batch before you cross

<Grid columns={2}>
  <Panel title="Many tiny calls" tone="coral"><div>Repeated dispatch</div><div>repeated argument conversion</div><div>repeated result handling</div></Panel>
  <Panel title="One coarse call"><div>one prepared buffer</div><div>one primitive over many entries</div><div>one compact result</div></Panel>
</Grid>

<Callout label="Amortize">The right batch moves frequency out of the FFI without moving policy into native code.</Callout>

<Notes>Batching is often misunderstood as native code taking over scheduling. It should not. TypeScript decides what belongs in the batch, prepares the storage, and invokes one coarse primitive. Policy remains visible; dispatch overhead is amortized.</Notes>

---

<Eyebrow>III · The result</Eyebrow>

## Marshalling disappears by design

<Grid columns={2}>
  <Panel title="Conventional binding" tone="coral"><div>Convert the object graph.</div><div>build native structs</div><div>run the primitive</div><div>rebuild result objects</div></Panel>
  <Panel title="Narrow edge"><div>Keep state in TypeScript.</div><div>share existing bytes</div><div>pass compact facts</div><div>return into the same state</div></Panel>
</Grid>

<Callout label="What disappears">No mirrored application objects. No serialized coordination state. No field-by-field result reconstruction.</Callout>

<Notes>This does not claim that an FFI call costs zero cycles. It means the architectural marshalling layer is absent. Large data stays in existing buffers, persistent identity stays in its owning runtime, and results are compact enough to return directly.</Notes>

<Eyebrow>III · Boundary smell</Eyebrow>

## A chatty FFI means the cut is wrong

<Grid columns={2}>
  <Panel title="Warning signs" tone="coral"><div>getters for every field</div><div>callbacks for every transition</div><div>mirrored trees and maps</div><div>wrapper objects in application code</div></Panel>
  <Panel title="Repair the cut"><div>lift decisions into TypeScript</div><div>batch related intentions</div><div>share one byte region</div><div>return one scalar or handle</div></Panel>
</Grid>

<Callout label="Diagnostic">If the binding needs an object mapper, move the boundary closer to the primitive.</Callout>

<Notes>Optimizing individual getters misses the architectural problem. A chatty interface indicates that coordination was placed below the boundary. Move it back up and expose a smaller native operation.</Notes>

# Native must earn the crossing

<Rule />

<Lead>Native code belongs where it provides a capability or implementation advantage large enough to repay the boundary.</Lead>

<Footer>Chapter IV · Necessity, leverage, and tradeoffs</Footer>

<Notes>Native is neither forbidden nor automatically preferred. It is an architectural trade. The implementation must provide enough value—system access, mature complexity, or dense computation—to justify the seam it creates.</Notes>

<Grid columns={2}>
  <Panel title="What native buys"><div>system access</div><div>mature implementations</div><div>predictable dense compute</div></Panel>

<Notes>The final chapter turns the architecture into a repeatable decision process. The unit of placement is an operation, not an entire subsystem, and the optimization target is the complete path.</Notes>

## Decide per operation, not per subsystem

<Eyebrow>Conclusion</Eyebrow>

# Keep native at the edges

<Rule />

<Lead>Let TypeScript own policy, lifetime, and coordination. Let native code touch the kernel, run the mature engine, or operate directly on shared bytes—then get out of the way.</Lead>

<Footer>One object graph · reused storage · narrow crossings</Footer>

<Notes>The architecture is a product of repeated performance work. One coordination model avoids mirrored state. Arenas and pools align reuse with visible lifetimes. Narrow FFI calls eliminate most marshalling. Native code remains powerful precisely because it is confined to work that earns the crossing.</Notes>
