## Getting nerd-sniped

<Notes>Like many Node.js devs, I've built many of my own personal JS runtimes over the years which I used as a place to experiment with ideas. I never really intended to release any of them publicly, but people keep insisting JS runtimes need to offload all their internal work to native code to be fast, so I decided I needed to disprove that.<br /><br />I'm going to share the runtime I've been building, and walk you through why a JavaScript-heavy core makes sense.</Notes>

---

## <a href="https://fino.fast">fino.fast</a> is...

<ul>
  <li>Near-zero native code apart from V8 bootstrap and FFI</li>
  <li>Heavy focus on layering, composition, and reusability</li>
  <li>Isolating performance optimization to shared layers</li>
  <li>Radically <i>large</i> core</li>
</ul>

<Notes>Fino is a runtime experiment which explores the idea of a large, heavily TypeScript core. It has near-zero native code apart from V8 setup and FFI infrastructure, and it focuses on layering, composition, and reusability. The aim is to demonstrate the compounding benefits of layered composability in complex systems, both from a design and a performance perspective.</Notes>

## What <i>is</i> in a runtime?

<Stack gap={1}>
<Callout title="Native Integration" variant="muted">connects native platform capabilities like socket and file system I/O</Callout>
<Callout title="Orchestration" variant="success">composes primitive native/platform actions into execution flows.</Callout>
<Callout title="Policy">validates, chooses behavioural routing, and manages failures.</Callout>
</Stack>

<Notes>To explain why avoiding native code makes sense, we need to understand what a runtime actually does. A typical JS runtime is constructed from a lot of internal infrastructure code, but the majority is not directly actually native or platform integration needs, it is orchestration and policy systems. Orchestration composes ergonomic behaviours from lower-level native capabilities and manages their work. Policy decides which behaviors apply and under what rules. Let's look at some examples...</Notes>

---

## Orchestration provides high-level abstractions

```ts
const body = new ReadableStream({
  async pull(controller) {
    const { bytes, done } = await read(fd);

    if (done) controller.close();
    else controller.enqueue(bytes);
  },

  cancel() {
    close(fd);
  },
});
```

<Caption>Native code exposes the capability. TypeScript defines how that capability behaves.</Caption>

<Notes>ReadableStream orchestrates individual read syscalls into a type representing ordered data flow. If that type was built in native code then every interaction with it would involve a jump to native code, but more importantly a mapping or conversion step between types on each side. Importantly though, none of that orchestration logic actually has any intrinsic benefit to being in native code. Node.js keeps that type changing cost relatively low by maintaining both native and JS representations in parallel, but that means twice the allocations and still frequently needs to marshal bits of data between the two.</Notes>

---

## Policy manages complex decisions

```ts
async function serve(socket, handler) {
  const tls = await nativeTls.handshake(socket, {
    protocols: ['h2', 'http/1.1'],
  });

  const driver =
    tls.protocol === 'h2'
      ? http2
      : http1;

  return driver.serve(tls, handler);
}
```

<Notes>Native TLS manages encryption and reports negotiated protocol of an http request. The runtime decides which things like protocol implementation to use and which fallback is acceptable. Those are routing and compatibility policies not directly relevant to the actual native work of making the networking syscalls. Keeping that in TypeScript means adding or changing protocols is very straightforward.</Notes>

## What actually benefits from native code?

<Stack gap={1}>
<Callout grow={1} basis={0} variant="muted" title="SIMD">Parsing, codecs, cryptography, compression, any vectorizable compute kernels</Callout>
<Callout grow={1} basis={0} title="FFI">syscalls, interfacing with existing C libraries, kernel or hardware interfacing</Callout>
</Stack>

<Notes>We of course need at least some native code to set up V8 and implement the FFI system. But some other scenarios can benefit. For example, TypeScript lacks SIMD so dense, repetitive computation scenarios like parsing, cryptography, compression, and codecs can benefit from native implementations. But the boundary can stay narrow: you can offload work which benefits from SIMD while keeping management of complex types in TypeScript. For example, the Ada URL parser in Node.js core essentially just provides a bunch of string indexes of where particular URL components are located and leaves it up to the consumer to turn that into a more useful higher-level representation. By thinking of ways we can offload expensive processing without creating correspondingly expensive data orchestration we can build faster systems. You might notice all these examples largely involve only two fundamental data types: buffers and pointers.</Notes>

## The temptation of native

<Notes>Native APIs expose pointers, borrowed memory, file descriptors, and other values with explicit lifetimes. That can make native wrappers around these feel tempting, but representation and lifetime are just orchestration concepts which don't actually need to live in native code. There's not often a performance benefit to orchestration or policy code living in the native side. Native code has a precise role. The temptation is allowing its representation and ownership concerns to pull unrelated orchestration across the boundary.</Notes>

---

## Native memory can stop at the boundary

```ts
class Sha256 {
  #context = native.createDigest('sha-256');
  #output = new Uint8Array(32);

  update(text: string) {
    native.update(this.#context, encodeUtf8(text));
  }

  hex(): string {
    native.finish(this.#context, this.#output);
    return toHex(this.#output);
  }
}
```

<Caption>A private pointer holds native state. A TypeScript buffer carries bytes. Callers exchange strings.</Caption>

<Notes>We can do wrapper types in TypeScript, using private class fields to store pointers and use them in class methods to transform low-level native interfaces into ergonomic TypeScript types. If we want TS to manage the lifetime of the allocation, we can simply use a buffer allocated from TS to hold the data filled by the native side.</Notes>

---

## TypeScript can own native handle lifetimes

```ts
class File {
  #fd: number;

  read(into: Uint8Array) {
    return readNative(this.#fd, into);
  }

  [Symbol.dispose]() {
    closeNative(this.#fd);
  }
}

using file = new File(fd);
await file.read(buffer);
```

<Notes>Descriptors which must be closed when done with them can also cleanly be wrapped in TS with resource management syntax. Native wrapping offers no inherent ownership advantage. We can use similar patterns to manage native-allocated memory which must be freed too, it's not really any easier to do manual memory management from native code than it is from TypeScript. You lose some things like destructors and smart pointers, but those ultimately all depend on V8 GC tracking, which can equally be done from within TypeScript.</Notes>

## Boundary costs are not where you think

```ts
const StatData = structType([
  ['mode', 'u32'],
  ['size', 'i64'],
  ['modifiedAt', Timespec],
]);

// Creates an ArrayBuffer of the right size and layout.
const data = StatData.alloc();
native.fstat(fd, data);

const size = Number(StatData.get(data, 'size'));
```

<Caption>Native fills bytes. TypeScript reads only the value it needs.</Caption>

<Notes>It's a common misconception that crossing the native boundary is inherently expensive. The real cost comes from translating rich types and ownership models between native and JavaScript representations. If you keep to primitive values and expose structs as byte buffers which can lazily be read from TypeScript, you can avoid most of the unnecessary marshalling work involved in shared operation on the same data. When the boundary carries simple values and buffers, composition and abstraction can be layered over it.</Notes>

## One validator can serve many systems

```ts
const inputSchema = v.object({
  name: v.string(),
});

const validator = compile(inputSchema);
const input = validator.parse(value);
```

<Caption>It can validate HTTP requests, MCP/tool inputs, JSON-RPC method parameters, workflow definition, and config loading.</Caption>

<Notes>An example of a highly generalized component is the JSONSchema-based validation module. It can be used for HTTP requests, CLI commands, AI tool call and MCP inputs, JSON-RPC method parameters, workflow inputs, and configuration loading from files, environment or CLI inputs. As the runtime accumulates more systems, more similar needs emerge between them, opening up further opportunities to generalize behaviours.</Notes>

## Composing reusable systems

```ts
app.post("/users")
  .value("body", body.json(inputSchema))
  .handle(async ctx =>
    Response.json(await users.create(ctx.body)));
```

<Caption>Body parsing and validation can compose into complex request routing.</Caption>

<Notes>With simple and reusable systems, you can build complex systems through composition. An HTTP router, for example, is very heavy on policy logic, which can be orchestrated through pipelining different reusable behaviours. Here we're composing body parsing and validation into the request handling pipeline.</Notes>

## Look for emergent patterns

```ts
const getPost = task({
  name: "get-post",
  inputSchema,
  cli: { positionals: [{ name: "name" }] },
  run: input => posts.get(input),
});

getPost.parse(argv.slice(2));
```

<Caption>Task owns invocation. The shared validator owns input checking.</Caption>

<Notes>A common pattern I saw in building this runtime was the need for named tasks in many cases such as CLI commands, LLM and MCP tool calls, background jobs, and runnable scripts. All benefitted from similar input validation, an identifying name, and some behaviour to run. If you watch for emergent patterns in complex systems you'll often find many such generalizable behaviours.</Notes>

## Realms are isolated execution contexts

```ts
const realm = new Realm({
  entry: './plugin.ts',
  overrides: importMap,
});

const result = await realm.call(input);
```

<Caption>Owns its own globals, module graph, and event loop, and can communicate with its parent realm.</Caption>

<Notes>In Fino, a Realm is a portable execution unit. It has its own JavaScript environment, globals, module graph, event-loop state and lifecycle. The parent selects an entry module, provides initial input, controls what can be imported from where and communicates through an explicit boundary.<br /><br />Two Realms can therefore execute the same application code with different capabilities or module implementations.</Notes>

---

## Import maps can remove or replace capabilities

```ts
const importMap = new ImportMap([
  {
    pattern: 'fino:process',
    directive: 'block',
  },
  {
    pattern: 'storage',
    directive: 'remap',
    target: 'storage/memory',
  },
]);
```

<Caption>Remove capabilities or replace implementations without changing their consumers.</Caption>

<Notes>Import maps manage module resolution policy. Blocking fino:process means code in this Realm cannot import the process module. Remapping makes the realm import the memory-backed storage implementation instead. The application needs no conditional imports or dependency-injection plumbing. Children can further restrict what they inherit, but cannot restore a capability denied by their parent. Fino also provides realm simulation capabilities, swapping out all I/O-producing modules in an import map with simulated ones, which is incredibly powerful for testing edge case scenarios.</Notes>

---

## Facades let the implementation live elsewhere

```ts
// Parent Realm
const secrets = new Facade('app:secrets', ['get'])
  .handle('get', name => vault.get(name));

const importMap = new ImportMap([
  { pattern: 'app:secrets', directive: secrets },
]);

// Child Realm
import { get } from 'app:secrets';
const token = await get('service-token');
```

<Caption>The child sees a module. The parent provides the capability.</Caption>

<Notes>A Facade goes further than remapping to another existing module. It presents a normal module interface inside the child while the implementation is directly owned by the parent. Calls cross the Realm boundary without application code knowing about messages or RPC.<br /><br />Simulation uses this pattern to replace fino:file with a parent-owned memory filesystem.</Notes>

## Approach performance holistically

<HStack gap={2}>
<Callout grow={1} basis={0} variant="muted">Measure and profile complete use cases</Callout>
<Callout grow={1} basis={0}>Keep logical kernels narrow and focused</Callout>
<Callout grow={1} basis={0} variant="success">Apply improvements broadly for maximal benefit</Callout>
</HStack>

<Caption>A fast primitive does not guarantee a fast system, efficient pipelines do.</Caption>

<Notes>Microbenchmarks are the bane of real-world performance. It's far too common for public interfaces to be designed around making the surface of that system fast in isolation, but may lack consideration for how the system will actually be used in real-world applications. A good example of this is async_hooks which on its own was able to be fast due to doing so little, but required so much layered on top of it to actually achieve the context management use case the majority of applications actually needed. AsyncLocalStorage manages to be much faster simply by optimizing for how it actually gets used.</Notes>

---

## As the core grows, subsystems shrink

<HStack gap={1}>
<Callout variant="muted">Keep native integration narrow</Callout>
<Callout>Generalize common/repetitive orchestration and policy</Callout>
<Callout variant="success">Build new capabilities by composition</Callout>
</HStack>

<Caption>Each new capability reveals reusable structure. Each reusable layer makes the next capability smaller.</Caption>

<Notes>Keep native integration narrow. Put orchestration and policy where they compose. The more you can route behaviour through shared systems the more improvement of those shared systems can have broader impact. The more you can generalize and reuse, the less code you need to write and maintain. A large core enables smaller individual subsystems.</Notes>

---

## Keep native boundaries narrow

<HStack gap={1}>
<Callout variant="muted">Stick to simple primitives like pointers and buffers</Callout>
<Callout>Only translate what you need when you need it</Callout>
<Callout variant="success">Build your pointer wrapper types in TypeScript</Callout>
</HStack>

<Notes>Native code doesn't need to be more than just basic FFI in almost all cases.</Notes>
